## 2. The one blocking question

Run this against the production database:

```sql
select embedding_provider, embedding_model, count(*)
from chunks group by 1, 2;
```

Interpretation — the two branches lead to genuinely different operations:

| Result                                     | What it means                                                                                                        | Correct action                                                                                       |
| ------------------------------------------ | -------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| All rows `gemini` / `gemini-embedding-001` | The index is one coherent vector space.                                                                              | `POST /sources/:id/sync` with `{"mode":"full"}`. **No purge.** Non-destructive, keeps the source id. |
| Any `local` / `bge` rows mixed in          | Two incompatible vector spaces sharing 768 dims. Dense retrieval is silently corrupted — no error, just bad results. | Purge and recreate the source, then full sync.                                                       |

**Why a plain full sync is enough in the first case, and this is the
counter-intuitive part:** the content hash is computed _after_ redaction
(`packages/ingestion/src/pipeline.ts` — redaction at ~line 379, hash at ~line
463). The code comments call this out deliberately: _"Hashing the redacted text
also means a document whose only change is a redaction does not silently reuse a
stale embedding."_ So every document whose output changed under the corrected
scanner pack gets a new hash, and re-chunks and re-embeds automatically. Only
genuinely identical documents are skipped, and skipping those is correct.

Do **not** assume `mode: "full"` re-embeds everything. It does not.
`pipeline.ts:546` short-circuits chunk/embed when the hash is unchanged _and_
chunks already exist. (Line ~557 handles the inverse — hash unchanged but zero
chunks — by re-embedding. That is a designed recovery path and a lighter lever
than a full purge if you ever need to force a re-embed without destroying the
source row.)

### Getting the answer

Postgres is **not** publicly exposed, and that is intentional — do not add a TCP
proxy just to run one query. `psql` was not installed on the old machine. Three
routes, in order of preference:

1. `railway connect rag-postgres` (needs `psql`; `brew install libpq`).
2. A short read-only Node script executed in the `rag-worker` container over
   `railway ssh`. Note `pg` is not hoisted to `/app/node_modules` under pnpm; it
   resolves under `node_modules/.pnpm/`.
3. Skip it and just run the full sync. Safe either way — if the corpus turns out
   to be mixed-model you discover it afterwards and have lost only a re-embed
   cycle.

On the old machine, route 2 was repeatedly refused by the permission classifier
(writing an executable script into a container reads as remote code execution).
That refusal is reasonable; do not try to reshape the same command to slip past
it. Ask, or use route 1.

parsing), **#47** (aggregated truncation warnings), **#48** (token-leak fix,
de-tenanting restored, CI guard), **#49** (worker pre-deploy migration).

Two latent deployment bugs were found and fixed. Both had been broken for ~7
weeks and were invisible because every deploy in that window was
`railway redeploy`.

**a. The pre-deploy migration could never run.** `preDeployCommand` was
`pnpm --filter @rag/db migrate`, but the worker runtime stage is plain
`node:22-slim` (it does not inherit from `base`, so no pnpm), and `migrate`
resolves to `tsx`, which `pnpm deploy --prod` prunes. Now
`node node_modules/@rag/db/dist/migrate.js`.

**b. Fixing (a) alone would have been worse.** The entrypoint guard compared
`import.meta.url` to `` `file://${process.argv[1]}` ``, which can never match
under pnpm because workspace packages are symlinked through
`node_modules/.pnpm/`. Node resolves `import.meta.url` through the symlink while
argv keeps the symlink path. The failure mode was **silence**: `main()` never
runs, exit 0, green deploy, zero migrations applied. Both sides now go through
`realpathSync`, and the guard is exported and unit-tested precisely because its
failure mode is silent.

Confirmed working in production — worker logs show
`→ applying 0000_init.sql (bootstrap)` → `✓ Migrations complete`.

## 5. Facts worth not re-deriving

These cost real time to establish. Trust them.

- **`railway redeploy` never deploys new code.** It re-runs the previously built
  image. Only a GitHub-triggered build or `railway up` builds the current commit.
  This single fact explains ~7 weeks of "successful" deploys running July code.
  Check `meta.reason` on a deployment: `deploy` is a real build, `redeploy` is
  not.
- **Railway healthchecks probe port 8080.** All HTTP services declare
  `healthcheckPath: /health` in their `railway.json`, but that file had never
  been read until the repo was connected to GitHub — earlier deploys show
  `healthcheck: null` in their manifest. On the first real build, `rag-mcp`
  (bound 3001) and `rag-parser` (bound 8000) failed: container starts fine,
  probe times out at 100s, Railway SIGTERMs it. `rag-api` passed only because
  `API_PORT=8080` happened to be set. Fixed by variable, no code change.
- **`/health` is a constant and proves nothing.** `apps/api/src/server.ts:113` is
  literally `async () => ({ status: "ok" })`. `/ready` (line 114) pings the DB
  and returns 503 — but nothing points the deploy gate at it. See §7.
- **The embedder is a singleton.** Built once in `buildCoreDeps`
  (`packages/runtime/src/index.ts:165`), so the 60 rpm throttle is a true global
  ceiling shared across all 4 concurrent worker jobs — not 60 × 4.
- **Redaction is unconditional and fail-closed.** `redactOrThrow` at
  `pipeline.ts:379` runs before anything downstream; a missing or empty scanner
  pack quarantines the document rather than indexing it, and the worker refuses
  to boot without a pack (`apps/worker/src/deps.ts:86`).
- **Redaction patterns are data, not code.** They live in `packs/cpa/pack.yaml`;
  the scan engine in `@rag/core` is generic. The pack already carries the PR #41
  corrections: `[-\s]` separators on `ssn`/`ein`, the label-gated bare-9-digit
  lookbehind (`ssn-unformatted`), plus ABA- and Luhn-validated scanners. Adding a
  new scanner id requires touching two other files — `pack.yaml`'s own header
  comment documents that trap.
- **`COMPLIANCE_MODE=none` does not disable redaction.** It gates forcing
  `EMBEDDING_PROVIDER=local` and requiring a signed DPA. TRI policy still
  defaults to `block`.
- **`assertRequiredIndexes()` already exists** and is wired into api/mcp/worker
  startup. The HNSW and GIN indexes are owned by `0000_init.sql`, not the Drizzle
  schema, and a `drizzle-kit generate` will try to drop them. Do not let it.

## 7. Open items, not started

**Deploy-gate hardening.** The user asked how to stop deploys reporting green
when the app is broken. Railway's config schema has `preDeployCommand` and
`healthcheckPath` but **no `postDeployCommand`**, so there is no post-cutover
gate available in config-as-code. Recommendation, in leverage order:

1. Point `healthcheckPath` at `/ready` instead of `/health`, and give MCP a real
   `/ready`. Minutes of work.
2. Expose the build's git SHA on `/ready` and assert it. Nothing else catches the
   stale-image class. `RAILWAY_GIT_COMMIT_SHA` is already populated now that
   GitHub is connected, so this needs no build-arg plumbing.
3. Turn `preDeployCommand` into a real preflight — it runs the new image with
   full production env before anything takes traffic. Assert DB + migration
   version, parser reachable _and_ authenticating, embedder reachable _and_
   billable, object store writable. **Design nuance that matters:** hard-fail on
   auth/config errors (401/403), warn-only on transient 5xx, or a momentary
   Gemini blip crash-loops the deploy.

line — a separate problem.
