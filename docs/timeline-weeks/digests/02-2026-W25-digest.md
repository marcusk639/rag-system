# Week 3 (W25): Jun 15 - Jun 17, 2026 — From Repo to Production

_The build week is over; this is the week the thing tries to go live — and mostly does._

## The Story

For two weeks the rag-system existed only as code that passed tests. Week 25 is the week it acquires an address.

The week opens, fittingly, where Week 2 left a thread dangling. Marcus had flagged that auth was being hand-rolled at the transport layer; Claude answers by lifting it into an abstraction. Between 2:41a and 3a on Jun 15 — a single dense session — the **AuthProvider** is born: a provider-neutral contract with three strategies (`static-token`, `oidc`, `composite`), wired through a factory and exported from `@rag/core`. The MCP HTTP transport is refactored onto it (1707–1712), an Express 4 async-middleware limitation gets wrapped, an async `scopeForRequest` gets its missing `await`, and a CryptoKey type that doesn't exist gets derived from the `jose` library. The config fails loud by design — `oidc` with no issuer throws at startup — and the whole thing lands documented in CLAUDE.md with a PR opened (1758). The Week 2 auth thread is resolved.

Then the meta-recursion: Claude runs a **full codebase learn-and-document pass** (S345), reading the monorepo end to end — DB layer, connector architecture, transport routing, parser sidecar, test harness — to understand the system it built. That knowledge feeds straight into deployment.

The center of gravity is **Railway**. Production Dockerfiles arrive for worker, MCP, API, and parser, each with a non-root `USER` (1791–1792, 1872) — though the build fights back first: missing `tsconfig` files in COPY stages break `@rag/core` until they're added to every image. Then Marcus logs into Railway (1864, 1875), creates the `rag-system` project, and Phase 2 begins in earnest (S375). Postgres-with-pgvector is provisioned; a persistent volume is added despite CLI syntax quirks; four services deploy. Postgres promptly **crashes on startup** — the volume mount clobbers initialization — and the fix is the classic one: point `PGDATA` at a subdirectory (1888). From there it's a grind of real deployment pain, each captured in the runbook: parser Dockerfile not found in the archive, API crash-looping on missing DB indexes, the `API_TOKENS` boot-order chicken-and-egg (worker won't start without it, can't set it before deploy), migrations that must run from the worker rather than the crash-looping API (1919), and a public TCP proxy that refuses to delete without an explicit service flag. By 10:56p Jun 16, **Phase 2 is complete — parser excepted** — four core services live and health-verified (1940, 1943).

Streaming and frontend land alongside. `POST /ask/stream` SSE work continues (S374); then in a single late session the **Next.js chat UI** is scaffolded — shadcn/ui, a server-side BFF proxy, SSE stream parser, ChatInterface with citations, KnowledgeBase orchestration (1949–1973). It's the cpa-knowledge-base shell finally reborn as promised, but it talks to a BFF, not yet to the live deployment.

The week closes on documentation: a verified architecture pass on hybrid retrieval and the worker process (1982–1983), and a **Phase 3 SharePoint go-live runbook** (1987) — Entra registration, Graph permissions, siteId resolution — written and committed, waiting on credentials that haven't arrived.

## Where We Are

It is mid-day on Jun 17, 2026, and the rag-system is, for the first time, running somewhere other than a test harness. Four core services — api, worker, mcp, postgres — are live and health-verified on Railway, Postgres carrying the pgvector extension on a persistent volume, migrations applied from the worker, GEMINI_API_KEY and API_TOKENS threaded through every Node service. The deployment runbook is no longer a plan; it's a field record of every crash and fix that got us here.

But the edges are unfinished, and honestly so. The **parser** is the one service Phase 2 explicitly excepted — its Dockerfile build context tripped the archive, and it's still being sorted; the system can serve and answer, but the ingestion path that feeds it real documents isn't fully wired in production. The **chat UI** exists — Next.js, shadcn, streaming, citations, a BFF proxy — but it points at a backend it hasn't been connected to live; the frontend-to-deployment seam is still open. **SharePoint**, the first real source, is one runbook away and one credential set short: Marcus is waiting on Entra app registration and MS_TENANT_ID / MS_CLIENT_ID / MS_CLIENT_SECRET before Steps 5–9 can run.

Older debts persist quietly underneath: the parser metadata type still crosses the boundary unvalidated, and the delta-cursor re-scan risk is unaddressed. Marcus's register has shifted again — from terse-orchestral to deployment-operator. He's logging into Railway, setting env vars, approving the Phase 2 commit, scheduling parser verification, and queuing Phase 3. He still hands off whole phases and trusts the agent to carry them, but the work is now operational, not architectural.

The thing has an address. It does not yet have its data.
