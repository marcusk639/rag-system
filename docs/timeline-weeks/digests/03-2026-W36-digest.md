# Week 4 (W36): Sep 02 - Sep 06, 2026 — The Day the Backups Went on Trial

_One CLI command refuses to connect, and four and a half hours later the project knows exactly how fragile its own recovery story is._

## The Story

Eleven weeks are missing here. Chapter 3 closed at midday on Jun 17 with four services live and no data; this chapter opens at 12:19p on Sep 2 with a system that clearly acquired data, users, and a surface area while nobody was taking notes. The record simply resumes mid-sentence. What the week lets slip is all second-hand: there is a `rag-backup` service now, and a `rag-documents` bucket. There are "audit-critical tables" worth a two-layer backup strategy (192). The `sources` table has grown multi-tenant and data-classification columns (214). There is a Teams integration far enough along to have a go-live PR (S736). And on Sep 6, almost in passing, comes the line that quietly settles chapter 3's biggest loose end: "web app already live" (3483). The chat UI got wired up. Nobody wrote down when.

The week itself is one day, and it starts with something small and stupid: `railway connect rag-postgres` fails with "No supported database found in service." Claude chases it properly — project not linked, CLI authenticated at 5.47.2, env vars set — then adds `DATABASE_URL` to the database service itself (109), which resolves cleanly and changes nothing (111). The real answer is uglier: the Railway CLI fetches `source.image` over GraphQL and matches it against a hardcoded keyword whitelist (118). `pgvector/pgvector:pg16` contains no keyword it recognizes (119). The tool was never looking at the database.

Marcus's response is characteristic of his new register: "Execute immediate swap" (S28). At 1:10p `rag-postgres` becomes `ghcr.io/railwayapp-templates/postgres-ssl:16.14`. It boots badly (144), then verifies clean — tables, indexes, extensions, vector search all functional (145) — `railway connect` works (147), and dependent services ride it out with nothing worse than expected connection drops (150).

Then the interesting damage surfaces. The new image is a different Debian, and a different glibc: every text btree index in the cluster is suddenly suspect. **postgres-ssl's `fork_collation_refresh()`** handles this automatically on restart — deferred, backgrounded, iterating every database, error-resilient (183, 184). It is a genuinely thoughtful piece of engineering that does the wrong thing: it runs `REFRESH COLLATION VERSION` _without_ reindexing, silencing the warning and erasing the only evidence a rebuild is needed. Claude reindexes by hand first, then lets the housekeeping run, and confirms all databases at collation 2.41 with zero invalid indexes (161, 186, 187). The lesson goes straight into CLAUDE.md as one of three new gotchas (203).

The rest of the day is about proving the system can come back from the dead. **pgBackRest** WAL archiving goes live against the Railway bucket rather than external S3 (225, 226) — two-config isolation, vCPU-tuned parallelism, async archiving with dual queue thresholds for transient outages, a WAL drop threshold auto-sized to 2307 MiB against a 4614 MiB volume (231, 236). First full backup archived successfully at 2:17p (235). Documented LIVE, committed as f3bbc61.

And then Marcus does the thing most projects skip: he makes it prove it.

The **PITR drill** is a four-hour humiliation with a good ending. Docker isn't running; started. The `postgres-ssl` image won't pull locally — timeouts, zero output, a likely daemon hang (287, 291, 292) — and the container that does exist lacks `python3`, breaking archive verification (289). The drill moves onto Railway. `rag-pitr-drill` is provisioned, crashes on a volume mount path mismatch (332), redeploys, reports SUCCESS, and exits anyway (339). It never enters recovery at all — it initializes a fresh PostgreSQL instead (337). When restore finally engages, it dies on file ownership: the backup manifest carries root-owned files while production PGDATA belongs to `postgres` (341, 350). A volume gets wedged and has to be deleted and recreated (343). Marcus, offered two debugging paths, picks the **cheaper manual root restore via Railway SSH** (S72) — the register is now incident commander with a budget.

At 4:26p it works. `pgBackRest` PITR restore succeeds when run as root against a fresh target directory (377), recovery replays, and the recovered database comes up intact with backup precision validated (386, 387). The finding that gets committed is careful and unflattering: **backups are proven restorable; the image's automated restore path is broken on Railway volumes** (388). Restore-by-hand is documented as the procedure. The drill infrastructure is torn down, production confirmed healthy (391, 393).

`railway connect rag-postgres` — the thing that started all of this — is still failing at 4:19p (369).

## Threads Continued / Opened / Resolved

**Resolved:**

- **Chat UI not wired to the live backend** (open since W25) — resolved somewhere in the eleven-week gap. Learned after the fact on Sep 6: "web app already live" (3483).
- **`railway connect` root cause** — diagnosed completely (image-name keyword whitelist, 118/119) and documented, though see below.
- **Collation/glibc index risk from the image swap** — reindexed, refreshed, verified at 2.41 with zero invalid indexes, and written into CLAUDE.md as a standing gotcha.

**Continued:**

- **Backup strategy** — moved from "documented in runbooks" to live WAL archiving plus a real drill. The permanent off-Railway destination is still blocked on admin consent (192), unchanged.
- **Documentation-as-artifact** — the day produced four runbook updates, three CLAUDE.md gotchas, and three commits whose payload is entirely findings.

**Opened:**

- **Automated PITR restore is broken on Railway volumes** — the headline debt. Recovery works only via a manual root procedure over SSH.
- **`railway connect` still fails post-migration** (298, 346, 369) — the migration fixed it at 1:11p and the failure returns by 2:57p. Unexplained.
- **Schema drift** — `ingestion_jobs` and `ingest_log` column mismatches surfaced during inspection (216) and were not addressed.
- **Teams go-live** — PR #56 under review (PORT fallback trap, manifest validation, TLS detection), and on Sep 6 the bot is blocked on an Azure subscription with seven config variables still unset (3485, 3487).

**Still open from earlier chapters:** parser metadata crossing the boundary unvalidated; delta-cursor re-scan risk. Neither appears this week. The parser service's fate is simply unknown from this record.

## Cliffhanger / What's Next

The sequencing decision on Sep 6 is the cliffhanger (3484): web app first, Teams tab second, bot last — because the bot cannot move until someone buys an Azure subscription. The infrastructure is sound and the backups are real, but recovery requires a human with root and a runbook, and nobody has yet asked what happens if that human is asleep. Meanwhile PR #56 sits mid-review, and the Teams bot service is provisioned, empty, and waiting on a purchase order.
