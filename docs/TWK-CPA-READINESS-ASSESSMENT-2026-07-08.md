## 2. The finding that still matters most — unchanged since 2026-07-04

This is a direct re-verification, not a re-quote. Confirmed today against `main` (`b5271e3`):

```

```

`sources.data_class` — the column whose own schema comment says `client_confidential` ingestion is refused at the pipeline level — is never read by the only real caller of the ingestion pipeline in production (`apps/worker`). Every document, from every configured source, is still processed as Class A, unconditionally, today. This is a small, well-scoped fix (the block logic and its six unit tests already work correctly in isolation) — reading `sources.data_class` in the worker and passing it as `sourceDocClass` into `runIngestion` is, per the original reconciliation's own estimate, "probably a few hours of work, not a redesign." It has simply not been done.

**The test-coverage review (§6.2 below) adds a new, important piece to this finding**: no test — not even after four more days of work across two separate implementation efforts — would have caught this being unfixed, because every e2e ingestion test drives the pipeline through a helper (`runOneIngestion`) that bypasses `apps/worker`'s handler entirely, and the worker's own unit test mocks `runIngestion` at a level that never inspects the `sourceDocClass` field. This explains, mechanically, why the gap has persisted through multiple rounds of otherwise-rigorous engineering: nothing in the test suite is structurally capable of noticing it's missing.

## 4. New technical findings (this pass)

Organized by domain. Each carries the severity the reviewing subagent assigned; severities are calibrated to a small (20-person), low-query-volume, non-DevOps-staffed deployment — not generic SaaS-scale defaults.

### 4.1 RAG architecture & retrieval quality (`llm-application-dev:ai-engineer` review)

- **HIGH — the compliance-mandated embedding path silently truncates every full-size chunk.** `CHUNK_SIZE` defaults to 800 tokens (`packages/core/src/config.ts:117`), but the local ONNX model (`Xenova/bge-base-en-v1.5`) — the _only_ embedding provider allowed when `COMPLIANCE_MODE=client-data` forces on-device inference (`packages/rag/src/embeddings/factory.ts:25`) — has a 512-token hard limit, and `embedBatch` (`packages/rag/src/embeddings/local.ts:118-131`) applies no explicit truncation control. transformers.js silently truncates to 512 at the tokenizer level. The stored chunk text (and therefore the sparse/BM25 side and the generator) sees the full 800 tokens; the dense vector reflects only the first ~65%. This is a systematic, invisible retrieval-quality degradation on exactly the path a CPA firm handling taxpayer data is required to use. **Fix: cap chunk size to ≤512 tokens whenever the local provider is active, or pass explicit truncation and fail loud on overflow instead of silently degrading.**
- **MEDIUM — large tables in Word/PDF SOPs get character-sliced, not row-preserved.** The table-aware chunker only activates for spreadsheet-origin documents (`composite-chunker.ts:42-48`); a table embedded inline in a `.docx`/`.pdf` SOP falls through to a sentence-boundary splitter that has no concept of table rows, and an oversized table ultimately gets cut at a raw character offset (`markdown-chunker.ts:187-206`). A fee schedule or depreciation table in a Word SOP can be sliced mid-row, stranding dollar figures from their labels.
- **MEDIUM — the citation filter can silently zero out the entire audit trail on multi-citation answers.** `filterCitationsToAnswer` (`generator.ts:89-98`) only matches `\[(\d+)\]` — a single-number bracket. LLM output styles like `[1, 2]`, `[1,2]`, or `[1-3]` (all common despite prompt instructions) match nothing, so every citation gets filtered out and the answer renders with zero sources. For a system whose citations are the compliance audit trail, a silently-uncited answer is a worse failure mode than a slightly-off one.
- **MEDIUM — no version/supersession awareness.** Documents are keyed by `(source_id, external_id)`; two differently-named files (`Engagement-SOP-2024.docx` vs. `-2025.docx`) are two distinct rows that both embed and both remain retrievable, with no effective-date or "is current" signal steering retrieval or generation away from the superseded one. This is the CPA-domain gap most likely to produce a confidently-wrong answer, since firms version SOPs as separate files routinely.
- **LOW/MEDIUM — `plainto_tsquery` requires every query term to match**, collapsing the sparse side of hybrid search to zero hits on verbose, real-world CPA questions (a question with 8+ words all needs to co-occur in one chunk). `websearch_to_tsquery` (OR semantics, phrase support) is the standard, low-effort fix.
- **Confirmed, hard evidence that the retrieval-eval numbers mean nothing yet**: the RRF dense/sparse weight sweep is **perfectly flat** — dense-only, sparse-only, and every blend in between produce byte-identical recall/nDCG numbers against the current `FakeEmbedder`-based harness, because the fake's "dense" vector is bag-of-words and therefore tracks the same signal as the sparse side. `RAG-VALIDATION-REPORT.md`'s Phase 3 (establish a real-embedder baseline, `docs/EVAL-BASELINE.md`) still has not been done. **The single highest-leverage, zero-cost next step for retrieval confidence**: the local ONNX provider requires no API key and no egress — swapping it into the eval harness in place of `FakeEmbedder` and rebuilding the corpus around 30–50 real (redacted) CPA questions would convert the existing, well-built eval machinery from theater into a real signal, immediately surfacing the 512-token truncation bug above in the process.
- **Sound, unmeasured, no defect found**: RRF fusion implementation, reranker interface and failure degradation, and the prompt-injection defenses (title/heading-path escaping included, not just body text) — all held up against direct adversarial construction attempts.

### 4.2 Security (fresh sweep, independent of the already-known compliance gaps)

- **MEDIUM — no minimum-length enforcement on the internal scope-JWT secret.** `internalScopeSecrets: z.array(z.string().min(1))` (`packages/core/src/config.ts:108`) accepts a 1-character secret. This HS256 key signs the _entire_ per-user confidentiality boundary (`allowedSourceIds`) for the web app. A weak key set by non-expert ops (a realistic scenario for this deployment) is brute-forceable offline from one observed token, and a forged token would grant cross-client access to every document in the system — a full confidentiality break of exactly the boundary the per-user-auth feature (PR #31) was just built to establish. **Fix: raise to `.min(32)` and mirror the check on the signing side, failing loud at startup.**
- **MEDIUM — no security headers on the web app.** No CSP, no `X-Frame-Options`, no HSTS (`apps/web/next.config.ts`). The authenticated chat UI is clickjackable in principle, and there's no CSP defense-in-depth layer against any future XSS.
- **LOW — upload MIME validation trusts the client-declared Content-Type**, not content-sniffed at the API boundary (though the parser sidecar does re-sniff with libmagic downstream, bounding the real impact).
- **LOW — no explicit Sentry PII-scrubbing hook**; real risk is low (SDK defaults are conservative) but not enforced by this codebase's own config.
- **Informational, not new**: `WEB_AUTH_MODE=static-fallback` is a real, complete bypass of per-user auth with no forced expiry — appropriate as an emergency rollback, but worth a hard expiry or deploy-time assertion so it can't be silently left on.
- **Clean bill, explicitly checked and confirmed sound**: OIDC JWT validation, static-token timing-safe comparison, connector injection surfaces, the Python parser's auth/subprocess hygiene, web-app XSS (react-markdown with no raw-HTML rehype plugin), CSRF on admin server actions, and storage-key path-traversal resistance.

### 4.3 Deployment & production readiness

- **HIGH — no verified backup/restore path for Postgres**, the sole store for chunks, embeddings, sources, and the compliance audit log. The team's own compliance plan (`docs/PLAN-CPA-COMPLIANCE.md`) already flags this open (CR-20, unchecked) — this pass confirms it's still open and adds that the deploy uses a raw Docker Postgres image on a Railway volume (not a managed plugin), so automatic-backup coverage is unverified, not just untested. **This should close before real client documents enter the pipeline, not after** — it's the single point of total, unrecoverable data loss in the system.
- **MEDIUM — the migration-timestamp bug (§1 above) has no permanent regression guard**, and CI is structurally blind to this exact bug class (it only ever cold-starts a fresh database; the bug only manifests on incremental application, i.e., real deploys). A ~15-minute fix (a monotonicity assertion in `migration-guard.test.ts`) closes a bug this codebase has already made twice.
- **MEDIUM — no alerting beyond Sentry's own channel.** Sync failures are captured correctly, but queue backlog and "sync succeeded but returned nothing" failure modes push notifications nowhere; nothing proactively tells the de facto one-person ops team (Marcus) anything is wrong.
- **MEDIUM — no documented rollback procedure**, though the actual mechanism (forward-only, additive migrations; Railway redeploy of a prior build for app-only regressions) is low-risk in practice — the gap is a missing paragraph in `docs/DEPLOYMENT.md`, not a missing capability.
- **Reassuring**: resource sizing is appropriately conservative for this pilot's real (low) scale; config validation fails loud in exactly the places that matter for a non-DevOps admin (confirmed the `API_TOKENS`-on-worker fail-loud design already caught a real misconfiguration during the actual Railway rollout, per `docs/PHASE-2-RAILWAY-RUNBOOK.md`); CI is green on `main`.

### 4.4 Test coverage

- **HIGH — the single most destructive, irreversible action in the system (`purge_source`, an MCP tool that permanently deletes a source and all its documents/chunks/history) has its authorization check completely untested.** `apps/mcp/src/server.test.ts` mocks the tool out entirely; no dedicated test exercises the `scope.enforcedSourceIds`-based permission gate in `apps/mcp/src/tools/purge-source.ts`. A scoped session that could bypass this check would silently and permanently destroy another client's data.
- **HIGH-risk category — three of four non-SharePoint connectors (Gmail, Outlook, Google Drive) have zero test files at all.** Pagination, cursor persistence, and error handling for these connectors are completely unverified.
- **HIGH — `packages/runtime/src/index.ts`'s `buildCoreDeps`/`buildAuthProvider` wiring** (the function every one of the three backend services calls to construct its dependency graph, including the auth-provider dispatch switch) is only ever exercised through a fully-mocked module in one worker test — a wiring bug here would not be caught by anything in the suite.
- **MEDIUM-HIGH — `GET /documents/:id` and `/documents/:id/download`** (the confidentiality-boundary-enforcing document-fetch and file-download routes) have no test at any layer, and the underlying S3 object-store read path is completely untested end-to-end.
- **Confirmed via test-coverage tracing**: no test currently exercises the _real_ `apps/worker` sync handler for the `sourceDocClass` gate (§2) — every e2e ingestion spec bypasses it via a direct-pipeline helper. A concrete two-part regression test is specified (unit assertion on the deps object passed to the real handler + an e2e test running the real handler, not the bypass helper) so the eventual fix for §2 ships with a test that would have actually caught the original bug.
- **Clean**: no skipped/only/todo tests anywhere in the suite (verified by grep, zero matches) — CI is not silently running a narrowed subset. The retrieval-eval harness is explicitly and honestly labeled as a synthetic smoke test everywhere it's referenced, including in the agent definition that runs it — no location was found presenting its numbers as real-world quality evidence.
